# 12 Days of Krampus

A responsive static website for **Ms. Mason’s AP Lang class** competition. It includes a public team leaderboard, PIN-protected team essay score entry, and a PIN-protected administrator workspace. Administrators alone manage extra points. The front end uses HTML, CSS, and vanilla JavaScript; Supabase provides the database, Row Level Security, and Edge Function authentication.

## Project layout

```text
index.html                         Public leaderboard
submit.html                        Team PIN portal
admin.html                         Administrator dashboard
css/                               Shared and page styles
js/                                Browser modules and scoring logic
data/teams.json                    Local team/member display-name mapping
supabase/schema.sql                Schema, seed data, RLS, and RPCs
supabase/functions/competition-api/ PIN verification and bootstrap function
scripts/bootstrap-credentials.mjs  One-time hidden PIN setup prompt
.github/workflows/deploy.yml       GitHub Pages deployment
```

## Security model and hosting boundary

GitHub Pages serves public files, so `js/config.js` contains only the Supabase project URL and publishable/anon key. Those values are public by design. Team and administrator PINs, their PBKDF2 hashes, the service-role key, and the JWT signing secret are never included in the site.

The `competition-api` Edge Function hashes and checks PINs, rate-limits failed attempts by client address and sign-in role, and signs a 30-minute Supabase JWT with only the team identity or administrator role. The browser holds that token in tab-scoped session storage. RLS limits authenticated table reads to the team in the token (or the administrator); unauthenticated visitors can read only the `public_leaderboard` view, which contains team name and overall score. Essay points are generated by Postgres, and submission RPCs validate ownership and lock the row in one transaction. Admin corrections and lock changes are written to the audit table.

This JWT approach needs the Supabase project’s legacy HS256 JWT signing secret to be enabled and configured as an Edge Function secret. Do not use the service-role key as the JWT signing secret. If the project is configured exclusively with asymmetric signing keys, create a compatible HS256 JWT secret for this project or adapt the Edge Function to use Supabase Auth users and sessions before launch.

## 1. Create and configure Supabase

1. Create a Supabase project at [supabase.com](https://supabase.com/). Save the database password in a password manager.
2. In **Project Settings → API**, copy the Project URL and publishable key (or legacy anon key). Never copy the `service_role` key into this repository.
3. Open **SQL Editor → New query**, paste all of `supabase/schema.sql`, and run it. The script creates seven placeholder teams, 29 placeholder members (Team 7 has five), 435 essay rows, and one extra-points row per team. It also installs the scoring constraints, private functions, RLS policies, and the public-only leaderboard view. If the project already has this app installed, run the updated script again after pulling code changes; it safely replaces the functions and policies without removing submissions. The current administrator score correction supports clearing a bad score so the team can resubmit it.
4. In **Project Settings → API → JWT Settings**, ensure the project supports HS256 tokens using its legacy JWT secret. Copy that secret only for the next Edge Function secret setup.
5. Install the [Supabase CLI](https://supabase.com/docs/guides/cli), sign in with `supabase login`, then link this folder to the project with `supabase link --project-ref YOUR_PROJECT_REF`.
6. Set the Edge Function secrets. Get the service-role key from the Supabase API settings and create a long random one-time bootstrap secret (at least 32 random characters). Put them in the ignored local file `supabase/functions/.env` (create the file; it is excluded by `.gitignore`), then push them to Supabase from that file:

   ```sh
   chmod 600 supabase/functions/.env
   supabase secrets set --env-file supabase/functions/.env
   ```

   The file should contain `COMPETITION_SERVICE_ROLE_KEY=...`, `COMPETITION_JWT_SECRET=...`, and `COMPETITION_BOOTSTRAP_SECRET=...`, one per line. Supabase supplies `SUPABASE_URL` to deployed Edge Functions. Never expose the service key in `js/config.js`; remove the local secret file when setup is complete.

## 2. Deploy the authentication function and initialize PINs

Deploy the function:

```sh
supabase functions deploy competition-api
```

The function must accept unauthenticated requests for the PIN login action. The PIN check itself is rate-limited and uses the service-role key only inside the function. The separate one-time setup action also requires the bootstrap secret header.

From a trusted local terminal, run:

```sh
node scripts/bootstrap-credentials.mjs
```

Enter the Edge Function URL, public anon/publishable key, bootstrap secret, administrator PIN, and each team PIN at the prompts. PIN input is hidden. Team names default to `Team 1` through `Team 7`; if you have already renamed them in the database, enter those exact current team names. Each PIN must be unique; team PINs must be at least four characters and the administrator PIN at least eight. The script sends credentials over HTTPS, and the function stores only salted PBKDF2 hashes.

The setup action can run only once. After success, remove `COMPETITION_BOOTSTRAP_SECRET` from Edge Function secrets with `supabase secrets unset COMPETITION_BOOTSTRAP_SECRET`. If setup is interrupted after it claims the one-time flag, inspect the credentials and, only if needed, reset `completed=false` in `credential_setup` through the Supabase SQL Editor and restore the bootstrap secret temporarily. PIN changes after initial setup should be performed by a trusted database administrator by updating the credential hash columns through a secure administrative process; never add a PIN to this repository.

## 3. Configure the browser and run locally

Edit the two public settings at the top of `js/config.js`. Copy **Project URL** from Supabase settings, which looks like `https://your-project-ref.supabase.co`; do not append `/rest/v1/` because the application adds its API paths itself.

```js
export const SUPABASE_URL = "https://YOUR_PROJECT_REF.supabase.co";
export const SUPABASE_ANON_KEY = "YOUR_SUPABASE_PUBLISHABLE_OR_ANON_KEY";
```

Use a local static server so browser modules load correctly. For example:

```sh
python3 -m http.server 8000
```

Visit `http://localhost:8000`. Test the leaderboard, each team PIN, essay score entry, admin extra points, corrections, and audit history. Never test with real competition scores until the competition is ready. The public view shows no standings until the first essay or admin extra-points entry is locked.

## 4. Team and member display names

Edit only `data/teams.json` to change the seven team names and 29 member names. Each team entry has its existing team UUID, a `database_name` alias used to match the public leaderboard (whose existing view does not expose team IDs), a local `name`, and member names keyed by the database `member_number`. Keep six teams at four members and Team 7 at five. Do not change IDs, database aliases, or member numbers. If a team has already been renamed in the database, the public leaderboard will show an “Unmapped team” fallback until the `database_name` alias is set to that current database label. The authenticated team and admin dashboards map by team UUID and member number, never array order.

The one-time bootstrap script maps PINs by the current database team names. If you rename teams before PIN setup, use those exact database names at the prompts. Do not rename teams while credential bootstrap is running.

**Privacy boundary:** The public Supabase leaderboard view contains only team name and total score, and the public page renders only rank, team name, and total score. Member names are not queried from Supabase for the public page. However, GitHub Pages is static hosting: `data/teams.json` is publicly downloadable. Do not put real member names in this file if they must be confidential from website visitors; hiding them behind the team/admin sign-in UI does not make the file private. Secure delivery of names would require a protected server-side source, which this frontend-only task does not add.

## 5. GitHub Pages deployment

1. Push this project to a GitHub repository and make sure `main` is the deployment branch (or adjust `.github/workflows/deploy.yml`).
2. In **Settings → Pages**, select **GitHub Actions** as the build and deployment source.
3. Push to `main`. The workflow runs `npm test` and JavaScript syntax checks, packages only the three HTML pages plus `css/` and `js/`, then deploys that artifact. Relative links and module paths work for a project subpath. Pull requests to `main` run the checks without deploying.
4. In the repository’s **Actions** tab, open **Build and deploy to GitHub Pages** to see the exact failed step if a run is red. Confirm the workflow file exists on `main`, the repository’s default branch is `main`, and **Settings → Pages → Build and deployment → Source** is set to **GitHub Actions**. The first deployment may need that Pages source setting before the workflow can publish.
5. Add the published site origin to Supabase **Authentication → URL Configuration → Site URL / Redirect URLs** if required by your project settings. The app does not use Supabase’s hosted sign-in redirect flow, but the site origin should still be registered for project consistency.

The browser’s publishable/anon key is intentionally public. Keep RLS and the exact `public_leaderboard` projection in place. Never put private values in GitHub Pages secrets expecting static JavaScript to hide them; anything delivered to a browser can be read by visitors.

## Scoring and data integrity

Raw score conversion is centralized in `js/scoring.js` and mirrored by a stored generated database column:

| Raw score | Competition points |
| ---: | ---: |
| 0 | 0 |
| 1 | 0 |
| 2 | 9 |
| 3 | 13 |
| 4 | 15 |
| 5 | 18 |

The database rejects scores outside 0–5. Teams submit one essay number at a time with one score for every member in a single atomic operation. The RPC verifies the signed team identity, recalculates points in Postgres, and locks all member scores for that essay together. Only administrators can enter, change, and lock extra points. Extra points are whole numbers, including negative values and zero, and are included in the public total after they are locked. The team dashboard shows essay totals only; its database response does not include extra points. Admin score corrections preserve the essay’s current lock state and are audited; administrators can also lock or unlock all team scores for an essay number together. Individual member totals remain inside the authenticated team/admin dashboard and are never in the public view.

Unlocking extra points clears the previous value so an administrator can enter and lock a new one. After updating the site code, rerun `supabase/schema.sql` in the Supabase SQL Editor to remove the former team submission function and restrict extra-point reads to administrators. Teams can use **Refresh** or return to their tab to see an administrator's latest essay changes.

For the five-person team, an administrator chooses one member’s score to exclude for each of the 15 essay numbers. The admin dashboard shows how many of the 15 selections have been made. Choosing a different member replaces the previous choice for that essay, and both changes are recorded in the audit log. Excluded scores still count in that member’s internal total and submission progress, but are omitted from the team total and public leaderboard.

## Administrator access

Use the shared **Log in** link in the site header. Entering the administrator PIN opens the admin dashboard; a team PIN opens that team’s score dashboard. The admin dashboard shows each team’s total, progress, extra points, member totals, essay scores, and pending essays. To clear a mistaken score, choose **Choose…** in that member’s score cell and click **Save scores**. After confirmation, the database clears and unlocks that score for team resubmission; other already-entered scores in the row are locked and audited. The team dashboard then offers the row for resubmission. Selecting a numeric score saves a correction while preserving its lock state. Group lock/unlock, correction, and re-submission actions require confirmation and create audit records with the administrator identity, affected team/essay/member, previous and new values, and timestamp.

## Backups and maintenance

Before and during the competition, create a Supabase database backup from the project dashboard, or use `supabase db dump --linked` from a trusted machine and store the resulting dump in encrypted storage outside this repository. Do not commit backups or credentials. Confirm backups include the database tables and audit log. Test a restore in a separate project before relying on it.

## Limitations to know before launch

- Sessions expire after 30 minutes; teams/admins can sign in again.
- Team and administrator credentials are initialized once by the Edge Function. Resetting credentials is intentionally an operator-only maintenance action.
- The app uses standard English number formatting and whole-number extra points.
- This repository cannot create your Supabase project, enter real PINs, or publish to GitHub on your behalf; those account-specific setup steps are yours to perform.
